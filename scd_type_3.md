# SCD Type 3: Add a "Previous Value" Column

---

## 1. First, what is an SCD?

### Fact tables vs dimension tables

A data warehouse splits data into two kinds of tables:

| Table type    | What it holds                         | Example                                         |
|---------------|---------------------------------------|-------------------------------------------------|
| **Fact**      | Events and measurements (numbers)     | `fact_sales`: order_id, store_key, amount, date |
| **Dimension** | Descriptive context (who/what/where)  | `dim_store`: store name, manager, region        |

Facts answer **"how much?"** and dimensions answer **"by what?"** (sales *by region*, *by customer*, *by department*).

### Why "slowly changing"?

Descriptive attributes do change, but rarely and at unpredictable times:

- a customer moves city
- an employee changes department
- a store is moved to a new sales region

A **Slowly Changing Dimension (SCD)** strategy answers one question:

> **When a descriptive attribute changes, what do we do with the OLD value?**

### The SCD types at a glance

| Type  | What happens on change                       | History kept?              |
|-------|----------------------------------------------|----------------------------|
| 0     | Never change the value                       | Original only              |
| 1     | Overwrite the old value                      | None                       |
| 2     | Add a new row (with start/end dates)         | Full history               |
| **3** | **Keep current + previous value in columns** | **One step back (limited)**|
| 4     | Move history to a separate history table     | Full (in separate table)   |
| 5     | Type 4 + Type 1 "current" pointer            | Full + current shortcut    |
| 6     | Types 1 + 2 + 3 combined                     | Full + current + previous  |

### Key terms used in these notes

| Term               | Meaning                                                                    |
|--------------------|----------------------------------------------------------------------------|
| **Natural key**    | The business ID from the source system (`emp_id`, `cust_id`, `store_id`)   |
| **Surrogate key**  | A number generated by the warehouse (`store_key`), used to join facts      |
| **Staging table**  | `stg_*`: the raw incoming data for this load                               |
| **Target table**   | `dim_*`: the dimension we maintain                                         |
| **MERGE**          | One SQL statement that updates matching rows and inserts new rows          |

---

## 2. What is SCD Type 3?

> **When a value changes, shift the current value into a "previous" column, then write the new value into the "current" column. All of this happens in the SAME row.**

```
Before:   current_dept = Sales      previous_dept = NULL
Change:   Sales  ──►  Marketing
After:    current_dept = Marketing  previous_dept = Sales
```

### Table structure

For each attribute tracked as Type 3, you add:

| Column            | Purpose                                     |
|-------------------|---------------------------------------------|
| `curr_<attr>`     | The latest value                            |
| `prev_<attr>`     | The value just before the latest change     |
| `<attr>_date`     | When the change happened (optional, but recommended) |

### Key characteristics

- **One row per entity**: the row count never grows because of changes (unlike Type 2).
- **Surrogate key never changes**: fact tables keep joining as before.
- **Only one step of history**: on a second change, the oldest value is pushed out and lost.

### Why use Type 3?

Type 3 is chosen when the business wants to **compare "old vs new" side by side**, typically around a single planned change:

- a sales-region **reorganisation**
- a product **re-categorisation**
- a company **restructure** (new departments)
- a customer **tier upgrade**, where marketing wants to know "upgraded from what?"

It gives that comparison **without the complexity of Type 2** (no date-range joins, no multiple rows per key).

### When NOT to use Type 3

- When you need **full history** (audit, compliance, "what was the value on date X?") → use Type 2.
- When an attribute changes **frequently**: history gets lost too quickly.
- When you need to correctly attribute **past facts to the value at that time**. Type 3 joins every fact to the current row, so it doesn't do this.

## 3. Example 1 (Basic): Employee department

`dept` is tracked as Type 3.

### Run 1: Source (`stg_employee`), 2026-10-01

| emp_id | emp_name | dept  |
|--------|----------|-------|
| E101   | Ravi     | Sales |
| E102   | Anita    | HR    |
| E103   | John     | IT    |

### Target after Run 1 (`dim_employee`)

| emp_id | emp_name | current_dept | previous_dept | change_date |
|--------|----------|--------------|---------------|-------------|
| E101   | Ravi     | Sales        | NULL          | NULL        |
| E102   | Anita    | HR           | NULL          | NULL        |
| E103   | John     | IT           | NULL          | NULL        |

### Run 2: Source (`stg_employee`), 2026-10-12

| emp_id | emp_name | dept          |
|--------|----------|---------------|
| E101   | Ravi     | **Marketing** |
| E102   | Anita    | HR            |
| E103   | John     | **Finance**   |
| E104   | Sneha    | Finance       |

### Target after Run 2

| emp_id | emp_name | current_dept | previous_dept | change_date |
|--------|----------|--------------|---------------|-------------|
| E101   | Ravi     | Marketing    | Sales         | 2026-10-12  |
| E102   | Anita    | HR           | NULL          | NULL        |
| E103   | John     | Finance      | IT            | 2026-10-12  |
| E104   | Sneha    | Finance      | NULL          | NULL        |

### MERGE code

```sql
MERGE INTO dim_employee t
USING stg_employee s
   ON t.emp_id = s.emp_id

WHEN MATCHED AND t.current_dept <> s.dept THEN
  UPDATE SET previous_dept = t.current_dept,   -- shift old value
             current_dept  = s.dept,           -- write new value
             change_date   = CURRENT_DATE

WHEN NOT MATCHED THEN
  INSERT (emp_id, emp_name, current_dept, previous_dept, change_date)
  VALUES (s.emp_id, s.emp_name, s.dept, NULL, NULL);
```

**Takeaways**
- In the `SET` clause, `t.current_dept` still refers to the **old** value, so `previous_dept = t.current_dept` captures it before it is replaced.
- Anita didn't change, so her row is untouched.
- Sneha is new, so she is inserted with `previous_dept = NULL`.
- ⚠️ `t.current_dept <> s.dept` is fine here only because `dept` is never NULL. If a department could be NULL (e.g. a new joiner not yet assigned), use `IS DISTINCT FROM`. See [Example 3, point 2](#2-null-safe-comparison-is-distinct-from).

> Priya's tier columns keep their June values because her tier didn't change in this run.

### MERGE code

```sql
MERGE INTO dim_customer t
USING stg_customer s
   ON t.cust_id = s.cust_id

WHEN MATCHED AND (   t.curr_city <> s.city
                  OR t.curr_tier <> s.tier
                  OR t.phone     <> s.phone ) THEN
  UPDATE SET
    -- Type 1: overwrite
    phone     = s.phone,

    -- Type 3: city
    prev_city = CASE WHEN t.curr_city <> s.city THEN t.curr_city  ELSE t.prev_city END,
    city_date = CASE WHEN t.curr_city <> s.city THEN CURRENT_DATE ELSE t.city_date END,
    curr_city = s.city,

    -- Type 3: tier
    prev_tier = CASE WHEN t.curr_tier <> s.tier THEN t.curr_tier  ELSE t.prev_tier END,
    tier_date = CASE WHEN t.curr_tier <> s.tier THEN CURRENT_DATE ELSE t.tier_date END,
    curr_tier = s.tier

WHEN NOT MATCHED THEN
  INSERT (cust_id, name, phone, curr_city, prev_city, city_date, curr_tier, prev_tier, tier_date)
  VALUES (s.cust_id, s.name, s.phone, s.city, NULL, NULL, s.tier, NULL, NULL);
```

**Takeaways**
- **The CASE statements are the key.** A row can have a city change without a tier change, so each Type 3 attribute decides **independently** whether to shift its value into "previous".
- Without the CASE logic, `prev_tier = t.curr_tier` would run for Priya in any update. If her phone changed, `prev_tier` would become `Platinum` and the real previous value `Gold` would be wiped out.
- This example still uses plain `<>`, which is **not NULL-safe**. If a customer deletes their phone (`'98450-11111'` → `NULL`), then `t.phone <> s.phone` returns **UNKNOWN**, the update is skipped, and the old number stays in the warehouse. Example 3 fixes this with `IS DISTINCT FROM`.

## 5. Example 3 (Real-world, 3+ years level): Store region realignment

### Business scenario

A retail chain **reorganises its sales regions** mid-year: "South" is split into "South-1" and "South-2". Finance wants to report each store's sales under **both the old and new region** for the rest of the financial year.

This "compare old vs new structure" requirement is **the classic real-life reason Type 3 is chosen.**

### Design

| Column          | SCD type | Notes                                   |
|-----------------|----------|-----------------------------------------|
| `store_key`     | Surrogate| `IDENTITY`, generated by the database   |
| `store_id`      | Natural key | From source                          |
| `store_name`    | Type 1   | Overwrite                               |
| `store_manager` | Type 1   | Overwrite, no history                   |
| `region`        | Type 3   | `curr_region`, `prev_region`, `region_eff_date` |
| `inserted_at`, `updated_at` | Audit | Load metadata                 |

### Real pipeline challenges handled

1. **Duplicates in the source**: the source is a **CDC feed**, so the same store can appear multiple times in a batch. The latest `op_ts` wins.
2. **NULL values**: a new store may not have a region yet.
3. **Reruns**: the job may fail and be re-executed with the same batch.
4. **Backfills**: an old batch may be loaded late.
5. **Audit columns**: track when each row was inserted or updated.

### Target DDL

```sql
CREATE TABLE dim_store (
    store_key        INT IDENTITY(1,1) PRIMARY KEY,
    store_id         VARCHAR(10) NOT NULL UNIQUE,
    store_name       VARCHAR(100),
    store_manager    VARCHAR(100),
    curr_region      VARCHAR(20),
    prev_region      VARCHAR(20),
    region_eff_date  DATE,
    inserted_at      TIMESTAMP,
    updated_at       TIMESTAMP
);
```

### Run 2 again (job failed midway and was rerun)

The same batch is processed a second time, and **the target stays exactly as shown above.** No row matches the change condition anymore, so nothing is updated. The load is **idempotent**.

### MERGE code

```sql
MERGE INTO dim_store t
USING (
    -- Step 1: keep only the latest record per store from this batch
    SELECT store_id, store_name, store_manager, region
    FROM (
        SELECT s.*,
               ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY op_ts DESC) AS rn
        FROM   stg_store s
        WHERE  batch_date = :load_date
    ) x
    WHERE rn = 1
) s
ON t.store_id = s.store_id

-- Step 2: update only if something actually changed (NULL-safe)
WHEN MATCHED AND (   t.curr_region   IS DISTINCT FROM s.region
                  OR t.store_manager IS DISTINCT FROM s.store_manager
                  OR t.store_name    IS DISTINCT FROM s.store_name ) THEN
  UPDATE SET
    -- Type 1 columns
    store_name      = s.store_name,
    store_manager   = s.store_manager,

    -- Type 3 column
    prev_region     = CASE WHEN t.curr_region IS DISTINCT FROM s.region
                           THEN t.curr_region ELSE t.prev_region END,
    region_eff_date = CASE WHEN t.curr_region IS DISTINCT FROM s.region
                           THEN :load_date ELSE t.region_eff_date END,
    curr_region     = s.region,

    -- Audit
    updated_at      = CURRENT_TIMESTAMP

-- Step 3: new stores
WHEN NOT MATCHED THEN
  INSERT (store_id, store_name, store_manager, curr_region, prev_region,
          region_eff_date, inserted_at, updated_at)
  VALUES (s.store_id, s.store_name, s.store_manager, s.region, NULL,
          :load_date, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);
```

> `stg_store` is assumed to have a `batch_date` column identifying each load. `store_key` is an `IDENTITY` column, so it is not in the INSERT list.

### What makes this production-grade

#### 1. Deduplicating the source (`ROW_NUMBER`)
A MERGE **fails** (or behaves unpredictably) if two source rows match the same target row. CDC feeds often send multiple updates per key in one batch, so always keep the latest record per key first.

#### 2. NULL-safe comparison (`IS DISTINCT FROM`)

**Short answer:** `<>` gives the wrong answer whenever a **NULL** is involved, and `IS DISTINCT FROM` gives the right answer every time. In SCD loads, using `<>` means **real changes are silently skipped**: no error, just bad data.

##### Why `<>` fails: NULL means "unknown"

In SQL, NULL doesn't mean "empty". It means **"I don't know the value."**
So when you ask "is *unknown* different from 'South-2'?", the database answers **"I don't know"**. That is a third result called **UNKNOWN**, which is neither TRUE nor FALSE.

A `WHERE`, `WHEN MATCHED AND ...` or `CASE WHEN` condition passes **only when the result is TRUE**. UNKNOWN is treated like FALSE, so the row is skipped.

##### Side-by-side comparison

| a (target) | b (source) | `a <> b`       | `a IS DISTINCT FROM b` | Did it really change? |
|------------|------------|----------------|------------------------|-----------------------|
| South      | South-2    | TRUE           | TRUE                   | ✅ Yes                |
| South      | South      | FALSE          | FALSE                  | ❌ No                 |
| **NULL**   | **South-2**| **UNKNOWN** ⚠️ | **TRUE**               | ✅ Yes                |
| **South**  | **NULL**   | **UNKNOWN** ⚠️ | **TRUE**               | ✅ Yes                |
| **NULL**   | **NULL**   | **UNKNOWN**    | **FALSE**              | ❌ No                 |

`<>` misses both **NULL → value** (a store gets its first region) and **value → NULL** (a region is removed).
`IS DISTINCT FROM` follows a simple rule: **two NULLs are the same, and NULL vs a value is different.** That's how a human would compare them too.

##### Store S104 with each operator

Target before Run 2: `S104 | curr_region = NULL | prev_region = NULL | region_eff_date = 2026-04-01`
Source in Run 2: `S104 | region = South-2`

❌ **Using `<>`**

```sql
WHEN MATCHED AND t.curr_region <> s.region THEN ...
--               NULL          <> 'South-2'  →  UNKNOWN  →  row skipped
```

| store_id | curr_region   | prev_region | region_eff_date |
|----------|---------------|-------------|-----------------|
| S104     | **NULL** 😱   | NULL        | 2026-04-01      |

The store was assigned to South-2, but the warehouse still says NULL. All of its sales show up under a "blank" region, and **no error is raised**.

✅ **Using `IS DISTINCT FROM`**

```sql
WHEN MATCHED AND t.curr_region IS DISTINCT FROM s.region THEN ...
--               NULL          IS DISTINCT FROM 'South-2'  →  TRUE  →  row updated
```

| store_id | curr_region    | prev_region | region_eff_date |
|----------|----------------|-------------|-----------------|
| S104     | **South-2** ✅ | NULL        | 2026-07-01      |

##### It matters inside the CASE too, not just the WHEN

```sql
prev_region = CASE WHEN t.curr_region <> s.region   -- UNKNOWN for NULL
                   THEN t.curr_region
                   ELSE t.prev_region END           -- falls to ELSE
```

A CASE also treats UNKNOWN as "not TRUE". Even if the row is updated because another column changed (e.g. the manager), the Type 3 shift logic **makes the wrong choice**. That's why this MERGE uses `IS DISTINCT FROM` in **both** the `WHEN MATCHED` condition and every `CASE`.

##### The same trap with `=`

```
NULL = NULL                      →  UNKNOWN  (not TRUE!)
NULL IS NOT DISTINCT FROM NULL   →  TRUE
```

This matters when you **join on a nullable column** or check "has nothing changed?".

| Want to check…       | Unsafe   | NULL-safe                  |
|----------------------|----------|----------------------------|
| Values are different | `a <> b` | `a IS DISTINCT FROM b`     |
| Values are the same  | `a = b`  | `a IS NOT DISTINCT FROM b` |

##### Database support

| Database                                        | NULL-safe "different"                           |
|-------------------------------------------------|-------------------------------------------------|
| PostgreSQL, Snowflake, SQL Server 2022+, DuckDB | `a IS DISTINCT FROM b`                          |
| MySQL, Databricks / Spark SQL                   | `NOT (a <=> b)`                                 |
| Oracle                                          | `DECODE(a, b, 0, 1) = 1`                        |
| Anywhere (fallback)                             | `COALESCE(a,'~') <> COALESCE(b,'~')`            |

> ⚠️ **COALESCE trick caution:** the placeholder (`'~'`, `-1`, `0`) must **never** appear in real data. For example, `COALESCE(discount_pct, 0)` treats "no discount recorded" (NULL) and "0% discount" as the same, so a change between them is missed.

> **Rule of thumb:** in SCD change detection, never compare nullable columns with `<>` or `=`. Use `IS DISTINCT FROM` (or your database's equivalent).

#### 3. Idempotent reruns
Because the update only fires when values differ, rerunning the same batch changes nothing.
Without that condition, a rerun would do `prev_region = curr_region`, copying **South-2 into prev_region**, and the real previous value "South" would be **lost forever**.
👉 This is one of the **most common Type 3 bugs in production.**

#### 4. `:load_date` instead of `CURRENT_DATE`
If you backfill or rerun an old batch a few days late, `CURRENT_DATE` stamps the **wrong** effective date. Using the batch's own date keeps it accurate.

#### 5. Mixed SCD types in one table
Real dimensions are rarely all one type. Here the manager is Type 1 and the region is Type 3, both handled in the **same MERGE**.

### Why the business wanted this: the report

```sql
SELECT d.curr_region,
       d.prev_region,
       SUM(f.sales_amt) AS sales
FROM   fact_sales f
JOIN   dim_store  d ON f.store_key = d.store_key
GROUP  BY d.curr_region, d.prev_region;
```

Sample output:

| curr_region | prev_region | sales     |
|-------------|-------------|-----------|
| South-2     | South       | 1,20,000  |
| South-2     | NULL        | 40,000    |
| West        | NULL        | 2,10,000  |
| East        | NULL        | 90,000    |

This shows sales under the **new** structure and how they map back to the **old** one, **without the date-range joins that Type 2 would require.**

## 6. Type 3 vs Type 1 vs Type 2

| Aspect                   | Type 1       | Type 2                    | Type 3                        |
|--------------------------|--------------|---------------------------|-------------------------------|
| On change                | Overwrite    | New row                   | Shift to "prev" column        |
| History kept             | None         | Full                      | One previous value            |
| Rows per entity          | 1            | Many                      | 1                             |
| Table growth             | New entities only | Every change         | New entities only             |
| Query complexity         | Simplest     | Needs date / current filters | Simple                     |
| Past facts reflect…      | Current value| Value at that time        | Current value (prev available)|
| Best for                 | Corrections, contact info | Audit, accurate history | Old-vs-new comparison   |

---

## 7. Pros and cons

| ✅ Pros                                           | ❌ Cons                                            |
|--------------------------------------------------|---------------------------------------------------|
| Easy old-vs-new comparison in a single row       | Only one level of history; older values are lost |
| One row per entity, simple joins                 | Schema change needed for every tracked attribute |
| Table doesn't grow on changes                    | Doesn't scale to frequently changing attributes  |
| Surrogate key stays stable                       | Past facts are not tied to the value at that time |
| No date-range joins                              | Reruns and NULLs can silently corrupt "prev" if coded carelessly (`<>` vs `IS DISTINCT FROM`) |

## 8. Real-world applications

1. **Sales territory / region realignment**: report under the new and old structure during transition.
2. **Product re-categorisation**: compare sales under the old and new category hierarchies.
3. **Organisational restructure**: employees' current vs previous department or cost centre.
4. **Customer loyalty tier**: "upgraded from Gold to Platinum" analysis.
5. **Chart of accounts changes** in finance: map old account codes to new ones.
6. **Price band / plan changes** in telecom or SaaS: current plan vs previous plan for churn and upgrade analysis.
7. **Store format changes**: e.g. "Express" → "Supermarket", comparing performance before and after.

## 9. Production checklist for Type 3

- [ ] Deduplicate source per natural key (`ROW_NUMBER() ... ORDER BY op_ts DESC`)
- [ ] Use NULL-safe comparison (`IS DISTINCT FROM` / `<=>` / `COALESCE`) in **both** the `WHEN MATCHED` condition **and** every `CASE`; plain `<>` silently skips NULL → value and value → NULL changes
- [ ] Update only when values actually differ (makes the load **idempotent**)
- [ ] Use a separate `CASE` per Type 3 attribute so each shifts independently
- [ ] Stamp effective dates with the **batch date**, not `CURRENT_DATE`
- [ ] Keep Type 1 and Type 3 columns clearly documented
- [ ] Maintain audit columns (`inserted_at`, `updated_at`)
- [ ] Test: new row, no change, single change, two changes, NULL → value, rerun
